# YASHIRIN — технический, UX и продуктовый аудит

## 1. Короткий вывод

Текущая версия — статический beta-сайт без backend и авторизации. Поэтому прямо сейчас нет поверхности атаки уровня «утечка базы пользователей» или «взлом аккаунта»: базы и аккаунтов пока нет. Основные текущие риски были в другом:

1. будущий пользовательский контент мог стать источником DOM-XSS из-за `innerHTML`;
2. отсутствовали защитные HTTP-заголовки;
3. внешние переходы и Telegram-flow были хрупкими;
4. формы не имели нормальной валидации и лимитов;
5. сохранённые места исчезали после обновления страницы;
6. автоматическая HEAD-проверка при возврате во вкладку могла лишний раз обращаться к серверу и перезагрузить страницу с незавершённой формой;
7. часть UX обещала функции, которых фактически ещё нет;
8. у travel-контента нет даты проверки — цена, режим работы и состояние дороги могут устаревать и подрывать доверие.

Версия в этом архиве закрывает P0-технические проблемы и часть наиболее очевидных UX-проблем, не меняя основную визуальную концепцию.

## 2. Что исправлено в коде сейчас

### Безопасность

- Добавлен строгий CSP без `unsafe-inline` для JavaScript и CSS.
- Добавлены `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `Referrer-Policy: no-referrer`.
- Добавлена `Permissions-Policy`, отключающая неиспользуемые camera/microphone/geolocation/payment/usb.
- JS и CSS вынесены из HTML.
- Удалён inline `onclick`.
- Убраны `innerHTML` из карточек и детальной страницы мест. Данные теперь вставляются через `textContent`/DOM API.
- Внешний programmatic open принимает только HTTPS и разрешённые домены.
- Все обычные внешние ссылки используют `noopener noreferrer` и `referrerpolicy="no-referrer"`.
- В формах добавлены `required` и `maxlength`.
- Нет API keys, access tokens, паролей или других секретов в клиентском коде.

### Надёжность

- Убран `setTimeout(...window.open...)`, из-за которого Telegram мог блокироваться popup-blocker'ом.
- Добавлен fallback для копирования текста, если Clipboard API недоступен.
- Удалена автоматическая HEAD-проверка новой версии при каждом возврате во вкладку.
- Фото вынесены из JS в отдельные файлы и могут кэшироваться отдельно.
- Сохранённые места теперь сохраняются в `localStorage` и остаются после перезагрузки.

### UX

- «реальное» заменено на более понятное «проверено».
- В карточках явно указано, что расстояние считается из Ташкента.
- CTA первого выезда теперь честно говорит, что открывает Telegram.
- Добавлено пояснение, какие детали пользователь получит после заявки.
- Убрана неработающая строка «Закрытый чат клуба».
- Убрано дублирование Rent Motors в профиле; партнёр остаётся в контекстном месте и в промокоде.
- В профиле больше нет фиктивного «0 поездок»; вместо этого объясняется, где хранятся сохранения.
- Форму обратной связи переделано с гипотетических вопросов «поехал бы / заплатил бы» на вопросы о реальном поведении, непонятных местах интерфейса и причине возвращаться.
- У формы «Предложить место» улучшены формулировки и обязательность полей.
- Добавлено предупреждение, что погода, режим работы и состояние дороги могут меняться.
- Увеличены минимальные touch-targets и добавлена поддержка `prefers-reduced-motion`.

## 3. Уязвимости, которые остаются не в коде, а в продукте

### P0. Доверие к информации

Сейчас в данных есть, например, цена входа, график работы и описание дорожного покрытия. Для travel-продукта это чувствительная информация: она устаревает.

**Что делать:**

Для каждого места добавить поля:

- `verified_at` — когда команда последний раз проверяла точку;
- `road_checked_at` — когда проверяли дорогу;
- `road_status` — нормально / осторожно / 4×4 / временно не рекомендуем;
- `price_checked_at` и `price_source`;
- `working_hours_checked_at` и источник;
- `car_type` — седан / кроссовер / 4×4;
- `season_notes`;
- `warning` — локальное предупреждение, если оно действительно нужно.

На карточке достаточно показывать: **«Проверено 4 дня назад»** или **«Дорога обновлена 2 сентября»**. Не показывать пользователю системные названия полей.

### P0. Пользовательские предложения

Когда появится backend, «Предложить место» станет UGC. Нельзя публиковать присланный текст/ссылки/фото напрямую.

**Что делать:**

`submitted → moderation → verified/rejected → published`.

Модератор должен отдельно проверять координаты, описание, доступность дороги, фото и потенциально опасные/закрытые территории.

### P0. Личная Telegram-учётка как инфраструктура

Сейчас ключевые действия ведут на `@yunusovprod`. Для beta это допустимо, но приложение не должно зависеть от персонального аккаунта одного человека.

**Что делать:**

На следующем этапе заменить на YASHIRIN Bot / официальный support account. Backend должен создавать заявку с ID, а Telegram использовать только как канал уведомлений.

## 4. Продуктовая архитектура: что должно быть главным

Главный сценарий YASHIRIN я бы зафиксировал так:

**Найти место → понять, реально ли туда ехать на моей машине → сохранить/построить маршрут → после поездки обновить состояние точки.**

«Выезды» и community должны усиливать этот сценарий, а не конкурировать с ним.

### Главный экран приложения

Не «лента всего», а быстрый выбор намерения:

- Куда съездить сегодня
- До 100 км
- На обычной машине
- С детьми
- Вода
- Горы
- На весь день

После выбора — карточки мест + карта.

### Карточка места

Минимальный набор до решения ехать:

1. фото;
2. расстояние и время от текущей/базовой точки;
3. тип машины;
4. состояние дороги;
5. последняя проверка;
6. сколько времени закладывать;
7. сезон;
8. платный/бесплатный вход;
9. CTA «Маршрут»;
10. CTA «Сохранить».

Вторичный контент — история, красивые описания, съёмочные точки, еда и т.д.

### Совместный выезд

До нажатия «Записаться» пользователь должен понимать:

- дата;
- время и точка старта;
- примерное возвращение;
- цена/бесплатно;
- нужна ли своя машина;
- можно ли пассажиром;
- сколько машин/мест осталось;
- подходит ли седан;
- кто организатор;
- что происходит после заявки.

Если какого-то из этих данных пока нет — лучше прямо показать «дату объявим после набора», чем писать просто «скоро».

## 5. Что не стоит делать сейчас

Пока не доказана регулярная ценность, не строить:

- полноценную социальную сеть;
- подписки на людей;
- комментарии под каждой точкой;
- сложную систему достижений;
- внутренние чаты;
- платную подписку;
- отдельное нативное приложение только ради самого факта наличия приложения.

Сначала продукт должен доказать, что пользователи возвращаются за данными о местах и дорогах.

## 6. Как получить настоящий feedback, а не вежливые ответы

### Кого тестировать

Первая волна: 10–15 человек из Ташкента.

Сегменты:

- 5 человек регулярно ездят за город;
- 5 ездят редко, но хотят;
- 3–5 человек без своей машины или готовые брать авто в аренду.

### Как проводить тест

Не презентовать продукт заранее. Дать телефон/ссылку и задания.

**Задание 1:** «Найди место, куда ты реально мог бы поехать в ближайшие выходные».

**Задание 2:** «Пойми, сможешь ли ты доехать туда на своей машине».

**Задание 3:** «Сохрани место и найди маршрут».

**Задание 4:** «Посмотри, как попасть на ближайший совместный выезд».

**Задание 5:** «Предложи своё место».

Во время теста нельзя помогать. Записывать:

- где человек остановился;
- что он ожидал увидеть;
- что понял неправильно;
- какие данные пошёл искать в другом приложении;
- на каком шаге перестал доверять информации.

### Что спрашивать после теста

1. Как ты обычно выбираешь место для поездки сейчас?
2. Что здесь заставило тебя сомневаться?
3. Какой информации не хватило, чтобы решить «еду»?
4. Что было лишним?
5. Что ты открыл бы здесь второй раз через неделю?
6. За какой информацией всё равно пришлось бы идти в Telegram/Instagram/Яндекс?

Не спрашивать как главный вопрос «нравится ли дизайн» и «пользовался бы приложением». Эти ответы плохо предсказывают реальное поведение.

## 8. План действий по этапам

### Этап 1 — сейчас, до массового трафика

1. Задеплоить эту исправленную версию.
2. После деплоя проверить, что `_headers` реально применяется хостингом.
3. Проверить CSP в DevTools: не должно быть CSP violations.
4. Проверить на iPhone Safari, Android Chrome и Telegram in-app browser.
5. Пройти все ссылки и Telegram-flow.
6. Проверить сохранение места после полного закрытия/повторного открытия сайта.
7. Для каждой опубликованной точки вручную проверить координаты, цену, график и дорогу.
8. Добавить дату проверки точки в данные.

### Этап 2 — первая пользовательская итерация

1. Подключить аналитику без PII.
2. Найти 10–15 тестеров.
3. Провести task-based тесты.
4. Свести все проблемы в таблицу: проблема / сколько пользователей столкнулись / тяжесть / экран / гипотеза решения.
5. Исправлять сначала проблемы, где пользователь не может завершить задачу, затем проблемы доверия, затем визуальные замечания.
6. Повторить тест ещё на 5 новых людях.

### Этап 3 — полезность вместо каталога

1. Добавить нормальную browser history/deep-link навигацию: системная кнопка/жест «Назад» должна возвращать с карточки места к списку, а ссылка на конкретное место должна открываться напрямую.
2. Добавить `verified_at` и road status.
3. Добавить фильтр по типу машины.
4. Добавить фильтр по расстоянию/времени.
5. Добавить внутреннюю карту.
6. Добавить «Был здесь недавно» с модерацией.
7. Добавить уведомление «состояние дороги обновилось» только пользователям, которые сохранили место.

### Этап 4 — backend

Минимальные сущности:

- users
- places
- place_verifications
- road_reports
- saved_places
- trips
- trip_members
- place_submissions
- moderation_actions

Обязательные меры:

- server-side validation;
- role-based access;
- row-level rules;
- rate limiting;
- audit log для модераторских действий;
- CSRF при cookie-auth;
- CORS только для нужных origins;
- secrets только server-side;
- backup базы;
- отдельные dev/stage/prod environments.

### Этап 5 — решение, нужно ли нативное приложение

Делать приложение, когда web-beta показывает повторное использование: пользователи сохраняют точки, возвращаются за дорогами/маршрутами и просят быстрый доступ/уведомления/offline.

Нативное приложение должно давать дополнительную пользу, а не просто копировать сайт:

- offline сохранённые маршруты;
- push о дороге/выезде;
- геолокация и точки рядом;
- загрузка road report с фото;
- камера/фото из поездки;
- навигационная интеграция;
- быстрый доступ к сохранённому.

## 9. Security checklist перед мобильным приложением

- Никаких API keys/секретов в клиенте, кроме публично допустимых mobile keys с ограничениями.
- Короткоживущие access tokens + безопасный refresh flow.
- Secure Storage/Keychain/Keystore для токенов.
- Certificate/TLS only; не разрешать HTTP fallback.
- Сервер не доверяет роли, координатам, ценам и статусам из клиента.
- Фото проходят type/size validation, перекодирование; EXIF удаляется по умолчанию.
- Rate limit на login, suggestions, comments/reports и media uploads.
- UGC проходит модерацию.
- Возможность удалить аккаунт и данные.
- Push-токены отделены от публичного профиля.
- Dependency/SAST scanning в CI.
- Логи не содержат access tokens, пароли и чувствительный пользовательский текст.

## 10. Проверки, выполненные на сборке

- `node --check app.js` — синтаксис JS валиден.
- HTML разобран парсером: обе формы и подключаемые файлы присутствуют.
- В HTML нет inline `onclick`.
- В JS/HTML нет `innerHTML`, `eval`, `new Function`, `document.write`.
- Нет hardcoded secrets по базовым сигнатурам.
- Внешние `target=_blank` ссылки имеют `noreferrer`/`noopener`.
- Фото вынесены в `assets/` и пути существуют.

Полноценный headless browser smoke-test в текущем окружении заблокирован системной browser policy, поэтому после деплоя обязательно пройти ручной smoke-test на реальном домене.
